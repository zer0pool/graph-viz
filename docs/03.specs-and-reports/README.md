# 03.specs-and-reports – 기능 명세 & 완성 보고서

**기능 개발의 계획(명세)→실행→검증(보고서) 사이클을 추적하는 폴더입니다.**

---

## 📋 구조

```
03.specs-and-reports/
├─ specs/              # 구현 전 작성하는 기능 명세서
├─ reports/            # 구현 완료 후 작성하는 결과 보고서
└─ README.md
```

---

## 📝 specs/ – 기능 명세서

**새 기능을 개발하기 전에 반드시 작성하는 설계 문서입니다.**

### 파일 명명 규칙
```
YYYY-MM-feature-name.md
예: 2025-01-job-detail-panel.md
```

### 파일 구조 (템플릿)
```markdown
# [기능명] - 기능 명세서

## 목표
- 이 기능이 해결하는 문제
- 사용자가 얻는 이점

## 범위
- 영향받는 시스템 (백엔드/프론트엔드/DB)
- 통합 지점

## 기술 설계
- 아키텍처 다이어그램
- API 엔드포인트 (신규/변경)
- 데이터 모델 변경
- 상태 관리 변경

## 구현 체크리스트
- [ ] 백엔드 엔드포인트
- [ ] 프론트엔드 UI
- [ ] 데이터베이스 마이그레이션
- [ ] 테스트 케이스
- [ ] 문서 업데이트

## 리뷰 완료자
- 아키텍트: @username (날짜)
- 리드: @username (날짜)
```

### 사용 방법
1. 새 기능을 개발하기 **전에** spec 파일 생성
2. 팀에 리뷰 요청 (PR 또는 이슈)
3. 피드백 반영하여 업데이트
4. 리뷰 승인 후 구현 시작

## 📊 reports/ – 완성 보고서

**기능 구현 완료 후 결과를 문서화하는 보고서입니다.**

### 파일 명명 규칙
```
YYYY-MM-DD-feature-name-completion.md
예: 2025-01-15-job-detail-panel-completion.md
```

### 파일 구조 (템플릿)
```markdown
# [기능명] - 완성 보고서

## 요약
- 구현된 기능 한 줄 요약
- 예상과의 차이사항

## 구현 결과
- ✅ 완료된 항목
- ⚠️ 부분적으로 완료된 항목
- ❌ 미완료 항목 (향후 계획)

## 기술 상세
- 실제 구현된 아키텍처
- 설계 변경사항 및 이유
- 성능 개선 결과

## 테스트
- 테스트 커버리지
- 버그 리포트 (있다면)
- 성능 테스트 결과

## 배포 정보
- 배포 날짜
- 배포 브랜치
- 마이그레이션 필요여부

## 교훈 & 향후 계획
- 배운 점
- 개선 아이디어
- 기술 부채

## 참고
- 관련 PR: #123
- 관련 이슈: #456
- 참고 문서: [링크]
```

### 사용 방법
1. 기능 구현 완료 후 보고서 작성
2. 실제 결과 vs 예상 비교
3. 배운 점과 향후 개선안 기록

- 변경사항 요약
- 성능 개선 결과

## 🔄 워크플로우

```
1️⃣ 기능 계획
   ↓
2️⃣ Spec 작성 & 리뷰 (specs/)
   ↓
3️⃣ 구현 시작 (개발 노트는 04.development-notes/ 에 기록)
   ↓
4️⃣ 구현 완료
   ↓
5️⃣ 완성 보고서 작성 (reports/)
   ↓
6️⃣ 배포 & 모니터링
```

---

## 💡 팁

- **Spec은 무조건 먼저**: 구현 시간 낭비 방지, 팀 모두가 방향 동의
- **Spec 리뷰가 중요**: 초기에 문제 발견 → 비용 절감
- **Report는 배운 점 기록**: 나중에 비슷한 작업 할 때 참고
- **누적 보고서 정기 업데이트**: 월 1회 또는 분기 1회
