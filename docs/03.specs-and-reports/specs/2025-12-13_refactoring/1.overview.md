## Current Problems

### 1. GraphService God Object

```python
# src/lineage_manager/services/graph_service.py
class GraphService:  # 1,653 lines, 38 methods
    def __init__(self, uow, job_manager):
        self.uow = uow
        self.job_manager = job_manager
    
    # Query methods (10 methods, ~600 lines)
    def get_job(...)
    def get_job_neighbors(...)  # 126 lines
    def get_table_neighbors(...)  # 123 lines
    def get_table_lineage_hierarchy(...)  # 132 lines
    def get_table_lineage_summary(...)  # 134 lines
    # ...
    
    # Mutation methods (6 methods, ~400 lines)
    def register_job(...)  # 102 lines
    def toggle_job_enabled(...)
    def set_table_trigger(...)
    # ...
    
    # Sync methods (9 methods, ~500 lines)
    def sync_from_lineage(...)
    def sync_single_job(...)  # 100 lines
    def sync_from_job_manager(...)
    # ...
```

**Issues**:
- ❌ Violates Single Responsibility Principle
- ❌ Hard to test (requires all dependencies)
- ❌ High maintenance complexity
- ❌ Many methods exceed 100 lines

### 2. Single Container Complexity

```python
# src/lineage_manager/core/container.py
class GraphContainer(containers.DeclarativeContainer):
    # Database
    database = providers.Singleton(Database)
    
    # Adapters
    job_manager_adapter = providers.Singleton(JobManagerAdapter)
    
    # Services (all domains in one container!)
    graph_service = providers.Factory(GraphService)  # Graph domain
    job_service = providers.Factory(JobService)      # Job domain
    user_service = providers.Factory(UserService)    # User domain
    bigquery_service = providers.Factory(BigQueryService)  # BigQuery domain
    
    # Auth
    oidc_provider = providers.Singleton(OIDCProviderClient)
```

**Issues**:
- ❌ Unclear domain boundaries
- ❌ Tests load all dependencies
- ❌ Limited scalability
- ❌ Difficult to split into microservices

### 3. Business Logic in Repositories

```python
# src/lineage_manager/repositories/table_repository.py
class TableRepository:
    def get_table_dag(self, table_name, max_depth, direction, ...):
        """139 lines of complex DAG construction logic"""
        # BFS traversal
        # Node/edge structure creation
        # Response formatting
        # ... business logic in repository!
```

**Issues**:
- ❌ Repositories should only handle data access
- ❌ Business logic mixed with data layer
- ❌ Hard to test

---

### 4. Single DB Connection Pool

```python
# src/lineage_manager/core/database.py
class Database:
    def __init__(self):
        self._engine = create_engine(
            settings.database_url,
            pool_size=10,  # Used by both reads and writes
            max_overflow=20,
        )
```

**Issues**:
- ❌ Read-only queries and write transactions share same pool
- ❌ Cannot utilize read replicas
- ❌ Pool exhaustion in read-heavy workloads

## Refactoring Goals

### 1. Clear Separation of Concerns

```
Before: GraphService (1,653 lines)

After:
├─ GraphQueryService (~400 lines)      # Read-only
├─ GraphCommandService (~400 lines)    # Mutations
├─ GraphSyncService (~400 lines)       # Synchronization
└─ GraphTraversalHelper (~200 lines)   # Shared helpers
```

### 2. Domain-Separated Containers

```
Before: GraphContainer (all services)

After:
├─ CoreContainer (Database, Config, Auth)
├─ GraphContainer (Graph domain)
├─ JobContainer (Job Manager domain)
├─ UserContainer (User domain)
└─ BigQueryContainer (BigQuery domain)
```

### 3. Pure Repositories

```
Before: TableRepository.get_table_dag() (139 lines of business logic)

After: 
├─ TableRepository: Pure data access only
└─ GraphQueryService.get_table_dag(): Business logic
```

### 4. Optimized Connections

```
Before: Single Pool (10 connections)

After:
├─ Write Pool: 10 connections (Primary DB)
└─ Read Pool: 20 connections (Read Replica)
```

## Three Major Improvements

### Improvement 1: Multi-Container Architecture

**Goal**: Separate containers by domain

**Estimated Time**: 18 hours (2-3 days)

**Key Tasks**:
- Create CoreContainer (Database, Config, Auth)
- Create JobContainer (JobManagerAdapter, JobService)
- Create UserContainer (UserService)
- Create BigQueryContainer (BigQueryService)
- Create GraphContainer (Graph services)
- Create ApplicationContainer (Root orchestrator)

**Benefits**:
- ✅ Clear domain separation
- ✅ Independent testing
- ✅ Easy to extend
- ✅ Microservice-ready

---

### Improvement 2: Service Layer Refactoring

**Goal**: Split GraphService and keep methods under 100 lines

**Estimated Time**: 25 hours (3-4 days)

**Key Tasks**:
- Create GraphTraversalHelper (consolidate BFS logic)
- Create GraphQueryService (query methods)
- Create GraphCommandService (mutation methods)
- Create GraphSyncService (sync methods)
- Remove business logic from repositories

**Benefits**:
- ✅ Improved code readability
- ✅ Easier testing
- ✅ Lower maintenance cost
- ✅ All methods under 100 lines

---

### Improvement 3: Connection Optimization

**Goal**: Separate Read/Write connections

**Estimated Time**: 8 hours (1 day)

**Key Tasks**:
- Create Write Engine (Primary DB)
- Create Read Engine (Read Replica or Primary)
- Separate Read/Write UoW
- Update containers

**Benefits**:
- ✅ 40% faster read queries
- ✅ 90% reduction in pool exhaustion
- ✅ 70% read replica utilization
